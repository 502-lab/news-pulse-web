# Feature Specification: 004 라우팅·인증 골격 (Routing & Auth Shell)

**Feature Branch**: `004-routing-auth-shell`

**Created**: 2026-06-14

**Status**: Draft

**Input**: User description: "Newsift 웹 프론트(React + React Router SPA)의 라우팅·인증 골격을 정의한다. 이후 모든 화면 기능이 이 골격 위에 올라가며, 이 단계에서는 개별 화면의 본문 UI가 아닌 접근 규칙·레이아웃·세션 동작만 다룬다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 게스트의 보호 라우트 접근 및 로그인 후 복귀 (Priority: P1)

미인증 사용자가 보호된 화면(예: 뉴스 홈)에 접근하려 하면 자동으로 로그인 화면으로 이동하고, 로그인 성공 후 원래 가려던 화면으로 복귀한다.

**Why this priority**: 서비스 접근의 가장 기본 흐름. 이 동작 없이는 인증 자체가 무의미하다.

**Independent Test**: 미인증 상태에서 `/home` 접근 → 로그인 화면으로 이동하고 URL에 returnTo 보존 → 로그인 성공 후 `/home`으로 복귀 확인.

**Acceptance Scenarios**:

1. **Given** 미인증 사용자가, **When** `/home`에 접근하면, **Then** `/login?returnTo=%2Fhome`으로 리다이렉트된다.
2. **Given** 로그인 화면에서 `returnTo=/home`이 있는 상태에서, **When** 로그인에 성공하면, **Then** 게이트 우선순위를 통과한 후 `/home`으로 이동한다.
3. **Given** `returnTo`가 없는 상태에서, **When** 로그인에 성공하면, **Then** 역할별 기본 홈으로 이동한다.
4. **Given** 미인증 사용자가, **When** 공개 경로(`/login`, `/register`, `/terms`)에 접근하면, **Then** 정상적으로 해당 화면이 표시된다.

---

### User Story 2 — 새로고침·탭 재오픈 후 세션 유지 (Priority: P1)

로그인한 사용자가 페이지를 새로고침하거나 탭을 닫고 다시 열어도 로그인 상태가 유지된다.

**Why this priority**: 매 새로고침마다 로그인을 요구하면 서비스 사용이 불가능한 수준이 된다. P1 흐름과 함께 앱 최소 동작의 전제 조건이다.

**Independent Test**: 로그인 후 페이지 새로고침 → 로그인 화면으로 이동하지 않고 기존 화면이 유지됨을 확인.

**Acceptance Scenarios**:

1. **Given** 로그인된 사용자가, **When** 브라우저를 새로고침하면, **Then** 세션이 자동 복원되어 현재 화면에 그대로 머문다.
2. **Given** 세션 복원 중(로딩)일 때, **When** 보호 경로에 접근하면, **Then** 로그인 화면으로 리다이렉트되지 않고 로딩 표시만 노출된다.
3. **Given** 저장된 갱신 토큰이 만료·회수된 상태에서, **When** 앱을 시작하면, **Then** 강제 로그아웃되어 로그인 화면으로 이동한다.
4. **Given** 세션 복원이 완료된 후, **When** 역할과 계정 상태를 확인하면, **Then** 접근 게이트 우선순위에 따라 적절한 화면으로 안내된다.

---

### User Story 3 — 로그인 성공 후 접근 게이트 순차 통과 (Priority: P2)

로그인에 성공한 사용자는 계정 상태(약관 재동의·이메일 인증·온보딩 완료 여부)에 따라 순서대로 필요한 화면으로 안내받고, 모든 조건을 충족한 뒤 역할별 홈에 도달한다.

**Why this priority**: P1 흐름(접근 제어, 세션 유지)이 동작해야 테스트 가능하며, 신규 가입자·약관 갱신 대상자에게 필수적인 흐름이다.

**Independent Test**: 약관 재동의가 필요한 계정으로 로그인 → 재동의 화면 이동 확인. 이메일 미인증 계정으로 로그인 → 이메일 인증 화면 이동 확인.

**Acceptance Scenarios**:

1. **Given** 로그인 성공 후, 약관 재동의가 필요한 계정일 때, **When** 게이트를 통과하면, **Then** 재동의 화면으로 이동한다.
2. **Given** 약관 재동의는 완료됐으나 이메일 미인증 계정일 때, **When** 게이트를 통과하면, **Then** 이메일 인증 화면으로 이동한다.
3. **Given** 이메일 인증은 됐으나 온보딩 미완료 계정일 때, **When** 게이트를 통과하면, **Then** 온보딩 화면으로 이동한다.
4. **Given** 모든 조건이 충족된 USER 계정일 때, **When** 게이트를 통과하면, **Then** 뉴스 홈(`/home`)으로 이동한다.
5. **Given** 모든 조건이 충족된 ADMIN 계정일 때, **When** 게이트를 통과하면, **Then** 운영 대시보드(`/admin`)로 이동한다.
6. **Given** 이미 로그인된 사용자가, **When** `/login` 또는 `/register`에 접근하면, **Then** 역할별 홈으로 리다이렉트된다.

---

### User Story 4 — 인증 토큰 자동 갱신 (Priority: P2)

API 요청 중 인증이 만료되면 사용자가 인지하지 못하는 사이에 자동으로 갱신되어 작업이 중단 없이 이어진다. 갱신에 실패하면 강제 로그아웃된다.

**Why this priority**: 토큰 만료가 사용자 작업을 중단시키면 서비스 품질이 치명적으로 저하된다.

**Independent Test**: 만료 직전 토큰으로 API 요청 → 자동 갱신 후 요청 완료. 갱신 실패 상황 → 로그인 화면으로 이동 확인.

**Acceptance Scenarios**:

1. **Given** 인증 토큰이 만료된 상태에서, **When** API를 호출하면, **Then** 사용자 인지 없이 토큰이 갱신되고 원래 요청이 완료된다.
2. **Given** 동시에 여러 API가 인증 만료 응답을 받았을 때, **When** 갱신이 시도되면, **Then** 갱신 요청은 단 1회만 수행되고 나머지 요청은 갱신 완료 후 순차 재시도된다.
3. **Given** 토큰 갱신이 실패했을 때, **When** 갱신 응답이 도착하면, **Then** 인증 상태가 초기화되고 로그인 화면으로 강제 이동한다.
4. **Given** 갱신이 성공했을 때, **When** 새 토큰이 발급되면, **Then** 기존 갱신 토큰은 새 갱신 토큰으로 교체 저장된다.

---

### User Story 5 — 역할별 레이아웃 분기 및 접근 제어 (Priority: P2)

USER와 ADMIN은 완전히 다른 레이아웃과 화면 구조에서 서비스를 이용한다. USER가 ADMIN 전용 화면에 접근하면 차단된다.

**Why this priority**: 역할별 경험 분리는 서비스의 핵심 구조이며, P1 흐름이 동작해야 테스트 가능하다.

**Independent Test**: USER 계정으로 `/admin` 접근 → `/home`으로 리다이렉트. ADMIN 계정으로 `/admin` 접근 → 좌측 사이드바 레이아웃 노출.

**Acceptance Scenarios**:

1. **Given** USER role 계정으로 로그인 후, **When** 모든 사용자 화면에 접근하면, **Then** 상단 GNB(5탭) + 프로필 메뉴 레이아웃이 표시된다.
2. **Given** ADMIN role 계정으로 로그인 후, **When** 관리자 화면에 접근하면, **Then** 좌측 사이드바(5메뉴) 레이아웃이 표시된다.
3. **Given** USER role 계정이, **When** `/admin/*` 경로에 접근하면, **Then** `/home`으로 리다이렉트된다.
4. **Given** auth·온보딩·오류·약관 화면에서는, **When** 어떤 역할이든 접근하면, **Then** 셸 없는 중앙 카드 레이아웃만 표시된다.

---

### User Story 6 — 로그아웃 (Priority: P3)

사용자가 프로필 메뉴에서 로그아웃하면 세션이 완전히 종료되고 로그인 화면으로 이동한다.

**Why this priority**: 보안상 필요하나 로그인 흐름이 동작한 후에 테스트 가능하며 서비스 핵심 동작에는 영향이 적다.

**Independent Test**: 로그인 상태에서 로그아웃 클릭 → 인증 상태 초기화 및 로그인 화면 이동 확인.

**Acceptance Scenarios**:

1. **Given** 로그인된 사용자가, **When** 프로필 메뉴의 로그아웃을 클릭하면, **Then** 서버에 로그아웃 요청이 전송된다.
2. **Given** 로그아웃 요청 완료 후, **When** 응답이 도착하면, **Then** 인증 상태와 토큰이 모두 초기화되고 로그인 화면으로 이동한다.
3. **Given** 로그아웃 API 요청이 실패해도, **When** 오류 응답이 도착하면, **Then** 클라이언트 측 인증 상태와 토큰은 동일하게 초기화되고 로그인 화면으로 이동한다.

---

### Edge Cases

- 세션 복원 중 네트워크 오류 발생 시: 게스트 상태로 폴백하고 로그인 화면으로 이동.
- `returnTo`에 ADMIN 전용 경로가 담겨있는 USER가 로그인 후: returnTo 대신 역할별 홈으로 이동.
- 동일 갱신 토큰으로 복수의 탭이 동시에 갱신 시도 시: 첫 번째 갱신만 성공하고 나머지는 새 갱신 토큰으로 재시도하거나 실패 처리.
- 접근 게이트 도중(예: 온보딩 중) 브라우저 뒤로 가기로 게이트 이전 경로 진입 시: 게이트가 다시 작동해 해당 단계로 재이동.
- 존재하지 않는 경로 접근 시: 셸 없는 404 화면 표시.

## Requirements *(mandatory)*

### Functional Requirements

**접근 제어**

- **FR-001**: 미인증 사용자가 보호 경로에 접근하면 시스템은 현재 경로를 `returnTo`로 보존하고 로그인 화면으로 리다이렉트해야 한다.
- **FR-002**: 로그인 성공 후 시스템은 아래 우선순위 순서로 접근 게이트를 검사해 해당 화면으로 안내해야 한다: 약관 재동의 필요 → 이메일 미인증 → 온보딩 미완료 → 역할별 홈.
- **FR-003**: USER role이 ADMIN 전용 경로(`/admin/*`)에 접근하면 시스템은 사용자 홈(`/home`)으로 리다이렉트해야 한다.
- **FR-004**: 이미 인증된 사용자가 로그인·회원가입 화면에 접근하면 시스템은 역할별 홈으로 리다이렉트해야 한다.
- **FR-005**: 공개 경로(로그인·회원가입·비밀번호 찾기·약관·개인정보·오류)는 인증 여부에 관계없이 접근 가능해야 한다.

**레이아웃 셸**

- **FR-006**: 인증·온보딩·오류·약관 화면은 셸 없는 중앙 카드 레이아웃(`AuthShell`)으로 표시되어야 한다.
- **FR-007**: USER 역할의 보호 화면은 상단 GNB 5탭과 프로필 메뉴가 포함된 레이아웃(`UserGnbLayout`)으로 표시되어야 한다.
- **FR-008**: ADMIN 역할의 보호 화면은 좌측 사이드바 5메뉴가 포함된 레이아웃(`AdminSidebarLayout`)으로 표시되어야 한다.

**세션·토큰**

- **FR-009**: 앱 시작 시 시스템은 보관된 갱신 토큰으로 토큰을 갱신하고 사용자 상태(`/me`)를 불러와 세션을 복원해야 한다.
- **FR-010**: 세션 복원 중에는 보호 경로로 이동해도 리다이렉트 없이 로딩 상태만 표시해야 한다.
- **FR-011**: API 요청이 인증 만료 응답을 받으면 시스템은 자동으로 토큰을 갱신하고 원 요청을 재시도해야 한다.
- **FR-012**: 동시에 다수의 API가 인증 만료 응답을 받아도 토큰 갱신은 1회만 수행되어야 한다.
- **FR-013**: 토큰 갱신이 실패하면 시스템은 인증 상태를 초기화하고 로그인 화면으로 강제 이동해야 한다.
- **FR-014**: 토큰 갱신 성공 시 새로 발급된 갱신 토큰으로 교체 저장해야 한다.
- **FR-015**: 로그아웃 시 시스템은 서버 로그아웃 API를 호출한 후 인증 상태와 모든 토큰을 초기화하고 로그인 화면으로 이동해야 한다. API 호출 실패 시에도 클라이언트 상태는 동일하게 초기화되어야 한다.

**라우트 슬롯 (본문 UI는 후속 단계)**

- **FR-016**: 설정 화면(`/settings`) 라우트 슬롯이 존재해야 한다 (본문 UI는 별도 spec에서 구현).
- **FR-017**: 이메일 인증 화면(`/verify-email`) 라우트 슬롯이 존재해야 한다 (게이트 목적지 전용).
- **FR-018**: 약관 재동의 화면(`/re-consent`) 라우트 슬롯이 존재해야 한다 (게이트 목적지 전용).

### Key Entities

- **AuthUser**: 인증된 사용자 — id, nickname, email, role(`USER`|`ADMIN`), emailVerified, onboardingCompleted, requiresReConsent
- **AuthState**: 인증 스토어 상태 — user(`AuthUser`|null), isLoading(세션 복원 중 여부), 로그인/로그아웃/갱신 액션
- **RouteGuard**: 접근 게이트 — 인증 여부·역할·계정 상태를 순서대로 검사해 통과 또는 리다이렉트를 결정하는 논리 단위
- **LayoutShell**: 레이아웃 컨테이너 — 역할과 화면 유형에 따라 적용되는 세 가지 셸(AuthShell / UserGnbLayout / AdminSidebarLayout)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 미인증 사용자의 보호 경로 접근 시 1회 렌더 이내에 로그인 화면으로 리다이렉트된다.
- **SC-002**: 로그인 성공 후 접근 게이트 통과 및 목적지 이동이 500ms 이내에 완료된다.
- **SC-003**: 페이지 새로고침 후 세션 복원이 완료되는 동안 보호 경로에서 로그인 화면으로 잘못 이동하지 않는다.
- **SC-004**: 인증 만료 상황에서 사용자가 진행 중이던 작업이 중단 없이 완료된다 (자동 갱신 성공 기준).
- **SC-005**: 동시 다발적 인증 만료 요청 상황에서도 갱신 API 호출이 정확히 1회만 발생한다.
- **SC-006**: USER가 ADMIN 전용 경로에 접근 시 1회 렌더 이내에 차단되고 사용자 홈으로 이동한다.
- **SC-007**: TypeScript 컴파일 에러가 0개이다.
- **SC-008**: 모든 라우트 가드 로직이 단위 테스트로 검증 가능하다 (UI 없이 순수 로직 테스트).

## Assumptions

- 이 단계에서 개별 화면(로그인 폼, 뉴스 홈 본문 등)의 UI는 구현하지 않는다 — 플레이스홀더 페이지로 대체.
- 백엔드는 로그인·토큰 갱신 응답 body에 accessToken과 갱신 토큰을 포함하며, httpOnly 쿠키를 사용하지 않는다.
- JWT claim에 `role`과 `emailVerified`가 포함되어 있어 클라이언트가 파싱해 즉시 사용할 수 있다.
- `GET /me` API가 `onboardingCompleted`, `requiresReConsent`, 프로필 정보를 응답한다.
- 이메일 인증 화면(`/verify-email`)·약관 재동의 화면(`/re-consent`)의 본문 UI는 후속 spec에서 구현한다.
- 설정 화면의 본문 UI는 후속 spec에서 구현한다(수정 API는 이미 존재).
- 기사 상세는 현재 인증 필요로 처리한다 (공개 접근 여부는 백엔드와 확정 후 별도 spec에서 반영).
- 검색, 북마크 영속화, 기사 비교 API, 계정 탈퇴는 백엔드 미구현으로 이 단계에서 제외된다.
- 001~003에서 구현된 컴포넌트(디자인 토큰, 공통 UI)를 재사용한다.
